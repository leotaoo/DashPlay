- 状态：**仅方案，未实施**（本文只记录设计，未改任何代码或设备）
- 设备：ZTE F50（SD 卡 OpenWrt + DashPlay，特斯拉模式）
- 目标：蓝牙名、CarPlay 图标、图标下方文字改为**在盒子上配置**，不再依赖每次升级后重跑脚本

## 一、为什么现在只能靠脚本

三样东西分处三个层，全都随程序发布：

| 要改的东西 | 现在的位置                                               | 形态        | 直接改的后果              |
| ---------- | -------------------------------------------------------- | ----------- | ------------------------- |
| 蓝牙名     | `/opt/dashplay/platform_debian.py` 常量 `BLUETOOTH_NAME` | Python 源码 | 升级覆盖                  |
| 图标       | `server-0.1.0.jar` 内资源 `f50-settings.png`             | 二进制资源  | 升级覆盖                  |
| 图标下文字 | `CarPlayServer.class` 常量池里的 `oemLabel`              | 编译产物    | 升级覆盖，且改 class 脆弱 |

因此现状是「改完能用、升级即失效」，只能每次重跑部署脚本（见 [F50-接收端图标替换-2026-11-05.md](F50-接收端图标替换-2026-11-05.md)）。

## 二、目标形态

盒子上留一份用户配置，程序每次启动读它：

```
/opt/dashplay/state/oem.json        {"label": "…", "bluetoothName": "…", "icon": "oem/icon.png"}
/opt/dashplay/state/oem/icon.png    180×180 PNG
```

- `state/` 是升级时**保留**的目录（`scripts/onecloud/firmware/upgrade.py`：`KEEP = ("state/", "identity/")`），配置与图片天然跨升级存活。
- 改完仅需 `/etc/init.d/dashplay restart`（3–5 秒）生效，不再动 jar。
- 缺省行为与现在完全一致：没有 `oem.json` 就用项目自带的图标与「盒子设置」。

## 三、改动清单

| 改动                                                                                              | 位置                                                                                      | 是否要重建 jar                        |
| ------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------- |
| 启动时读取 `state/oem.json`：`label` 覆盖 `oemLabel`；`icon` 存在则读文件字节，否则回退类路径资源 | 新增 `patches/playport-oem-overrides.patch`（改 `CarPlayServer.kt`，约 30 行 + 1 个测试） | **要**（`scripts/build-playport.sh`） |
| 蓝牙名从同一份 JSON 读，缺省 `DashPlay`                                                           | `scripts/onecloud/platform_debian.py`（`BLUETOOTH_NAME` → 启动时解析）                    | 不用                                  |
| 设置页「外观 / 名称」：两个输入框 + 图标上传 + 保存后重启接收端                                   | `scripts/onecloud/settings_page.py`、`settings_ui.py`                                     | 不用                                  |
| 随包分发                                                                                          | 现有 bundle 流程自动收录 `scripts/onecloud/*.py`                                          | 不用                                  |

可行性依据（已在代码中确认）：

- `ServerConfig` 有 `stateDir` 字段，接收端启动时能定位到 `state/`（多处测试已用 `ServerConfig(identityDir=…, stateDir=…, …)`）。
- 设置页 UI 是 Python 生成的 HTML（`settings_ui.py: portal_page`），加表单不需要重建 web 前端。
- `oemLabel` 与图标都在 `CarPlayServer` 构造 `AirPlayConfig` 处一次性传入，覆盖点唯一、改动面小。

## 四、必须守住的约束

1. **默认永不失败**：文件缺失、JSON 损坏、PNG 尺寸不符、读取异常——一律回落到项目自带图标与「盒子设置」，只写一行日志。用户配置坏掉不能导致接收端起不来。
2. **180×180 强校验**：接收端对车机声明的是 180×180；上传时校验一次，加载时再校验一次，不符则拒用并回退。
3. **商标不进仓库**：仓库只加「读取文件」的机制，默认图标仍是项目自己生成的那张；第三方图标只存在于用户的 `state/oem/`，不进发布包、不随仓库分发。
4. **重启才生效**：接收端在启动时读取一次，改完需要重启；设置页保存后如自动重启，必须事先提示「CarPlay 会短暂断开」。
5. **蓝牙改名后手机仍要重配**：iOS 在配对时记住名字，属于系统行为（见 [F50-设备名称与显示名-2026-11-05.md](F50-设备名称与显示名-2026-11-05.md)）；设置页应给出这句提示，否则用户会以为没生效。

## 五、风险

- **改动落在启动路径**：`CarPlayServer` 构造处异常会直接让接收端起不来。缓解：默认回退 + 单元测试（文件缺失 / JSON 坏 / 尺寸错 / 正常四类）+ 安装包升级失败自动回滚（`upgrade.py` 已有机制）。
- **一次重建**：需要 Docker + JDK 25 按 `scripts/build-playport.sh` 出 jar，构建由用户执行。
- **命名空间冲突**：`oem.json` 与现有 `state/*.json`（`hotspot.json`、`ddns.json`、`update-check.json` 等）并存，需在文档与代码注释里写清归属。

## 六、分步实施建议

1. **第一步：文件驱动**（范围小，能力已完整）
   - 一处 patch（label + icon）+ `platform_debian.py` 读 `bluetoothName`；
   - 用法：SSH 写 `state/oem.json`、放 `state/oem/icon.png`、重启；
   - 验收：改 label/icon/BT 名各一次，重启后车机与手机分别核对；删掉 `oem.json` 后回落到默认。
2. **第二步：设置页 UI**（可选）
   - `settings_ui.py` 加「外观 / 名称」卡片：文本输入 + 图标上传（`<input type=file>`）+ 保存；
   - `settings_page.py` 处理 POST：校验 180×180、写入 `state/oem/`、写 JSON、按需重启；
   - 验收：网页上传一张 180×180 与一张 512×512（后者应被拒并提示）。

## 七、被否掉的替代方案

- **让脚本在升级后自动重放**：仍然依赖外部脚本、且要处理「升级完成」的钩子；本质没解决问题，只是把手工换成自动。
- **在盒子上改 class 常量池**：可以做到（常量池条目是「长度 + 内容」，无绝对偏移依赖），但每次升级都要重做，且改坏了接收端起不来——只适合一次性试验，不适合作为产品能力。
- **改 `state/receiver/config.json`**：`run-receiver.py` 每次启动都重写该文件，改了不生效，容易误判。
