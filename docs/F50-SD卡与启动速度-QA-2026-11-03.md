# F50：换更快的 SD 卡对启动速度的影响（QA）

- 日期：2026-11-03
- 适用：ZTE F50，SD 卡启动 OpenWrt + DashPlay
- 性质：问答记录；结论按启动链与仓库实测数据推断，仓库内**没有** SD 卡基准测试
- 相关：[F50-刷CarPlay原理-2026-11-03.md](F50-刷CarPlay原理-2026-11-03.md)、[F50-系统结构与后台-2026-11-03.md](F50-系统结构与后台-2026-11-03.md)

## Q1：换一张更快的 SD 卡，启动会明显变快吗？

**不会明显变快，通常是几秒级（乐观 3–6 秒），量级不变。**

F50 的内核在 `boot_a`（eMMC），只有**根文件系统在 SD 卡上**，所以读卡只发生在用户空间阶段。README 实测整机「通电约 37–44 秒进入 CarPlay」，其中大部分是固定开销。

## Q2：那 37–44 秒具体花在哪？哪些和卡有关？

| 阶段 | 主导因素 | 快卡有帮助吗 |
|---|---|---|
| BootROM → bootloader → 内核 | eMMC、CPU、固定初始化 | 无 |
| OpenWrt 用户空间（procd、hostapd、DHCP） | 大量小文件随机读 | 有一点 |
| supervisor（Python 启动与导入） | `.py` 与模块读 | 小 |
| 蓝牙初始化 | rfkill 复位 + UART 上传厂商固件 | 无（受串口与芯片限制） |
| **Java + PlayPort 启动** | JRE、几十个 jar、上千 class 的**随机读** + AppCDS 归档 | **主要收益** |
| 蓝牙握手 / Wi-Fi 交接 / 会话建立 | iPhone 侧、射频、mDNS | 无 |
| 车机浏览器打开网页 | 车机自身 | 无 |

关键证据：`scripts/onecloud/run-receiver.py` 注释写明 AppCDS 归档失效时**每次启动多花约 3 秒**——Java 类加载本身就是 3 秒级的分量，这也正是快卡唯一能明显压缩的部分。

## Q3：哪些部分是"写死的"，换卡完全无感？

- 蓝牙冷启动：快路径 0.2 s；退回厂商节奏则 1 s + 2 s（`board_zte_f50.py`）。
- mDNS 广播、RTSP 监听、iPhone 应答、CarPlay 会话建立：取决于射频与 iPhone，不取决于磁盘。
- 内核与 bootloader：读 eMMC。

## Q4：那到底值不值得换？

分两种情况：

- 现在的卡是**正规 A1 以上**：也许只省 3–6 秒，性价比一般。
- 现在是**杂牌 / Class 10 / 老卡**：随机 4K 往往很差，收益更大——而且更该换的理由在 Q5。

## Q5：比"快"更重要的是什么？

**稳定性。** SD 卡在这台机器上是整个根文件系统，不只是启动盘：

- 卡慢或老化 → Java 启动、状态文件保存（`durable_write` 会 fsync）、诊断日志定期落盘都会卡。
- 卡不稳定 → 启动失败，而 OpenWrt **连续 5 次起不来会自动回退到原厂 Android**。

第二条尤其要记住：表现是"偶尔开机进了原厂系统"，很容易被误判成刷机或分区问题，实际可能是卡接触不良或在退化。

## Q6：买什么卡？

| 项 | 建议 |
|---|---|
| 规格 | A2 + U3、UHS-I 即可——F50 的 SD 接口大概率就是 UHS-I，UHS-II/III 不会更快 |
| 容量 | ≥8 GB（安装脚本硬性要求 7.5 GB 以上），32 GB 足够 |
| 类型 | 优先「高耐用 / high-endurance」（行车环境反复写日志与状态） |
| 避免 | 杂牌、扩容假卡、microSD 转 SD 卡套、二手卡 |
| 注意 | 卡会被**整个清空**并新建 ext4，原数据必须先自行备份 |

## Q7：怎么自己量出差异？

supervisor 日志每行带「内核启动后第几秒」，接收端日志带「JVM 启动后毫秒」：

```sh
ssh root@100.96.0.1 'grep -E "^boot |bluetooth powered" /var/run/dashplay/supervisor.log'
ssh root@100.96.0.1 'grep -nE "RTSP listening|CarPlay is live" /var/run/dashplay/receiver.log'
```

每次开机的完整日志也留在 `/opt/dashplay/state/logs/<时间>/`。

对比方法：换卡前后各做几次**冷启动**（断电极冷启，不要热重启），看两个差值：

| 看什么 | 结论 |
|---|---|
| `supervisor start` 到 `CarPlay is live` 差值基本没变 | 瓶颈不在卡，多半是蓝牙握手或 iPhone 侧 |
| Java 启动那段明显缩短 | 卡确实是瓶颈，这次换卡有效 |
| `supervisor start` 本身就很晚 | OpenWrt 用户空间启动慢，值得换卡 |

补充检查（确认 AppCDS 是否在起作用，失效会白白多花约 3 秒）：

```sh
ssh root@100.96.0.1 'grep -i "mismatch\|sharing" /opt/dashplay/state/receiver/cds.log'
```

## Q8：如果不想换卡，还能从哪挤出时间？

按收益排序，这些都比换卡明显：

1. 让 AppCDS 归档保持有效（jar 一变就重建，见上面那条检查）。
2. 保持最新正式版程序——启动相关补丁（后台起 mDNS、early receiver 等）都在版本里。
3. 减少不必要的外设/服务占用，保证供电稳定（F50 冷启动对供电敏感）。
4. 检查 Wi-Fi 信道与蓝牙配对状态，握手阶段才是 44 秒里波动最大的部分。

## 一句话结论

换快卡主要买到的是**可靠性**，启动时间顺带省几秒；指望靠它把 37–44 秒压到 20 秒不现实，真正的固定开销在蓝牙初始化、Java 启动和 iPhone 握手。
